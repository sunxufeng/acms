# ACMS 数据存储迁移方案：飞书 Base → PostgreSQL

> 状态：**阶段 0–4 已完成并上线**（2026-09-07 23:00 全量切到 PostgreSQL）
> 创建：2026-09-07
> 决策：全量迁移，飞书 Base 降级为导入源
>
> 实际结果：生产 **79 张表 / 1558 行 / 1333 字段**（摸底发现比 contracts 登记的 41 张多 38 张），
> 全量导入后「行数比对 + 抽样逐字段比对」**全部通过**。
> 待办：观察 24h 无异常后把 `SQL_SHADOW_WRITE` 改为 `0` 并重启 ＝ 阶段 5 彻底下线飞书写入。

## 一、前提修正：2 万不是硬顶，是版本配额

| 版本 | 单表行数上限 |
|---|---|
| 商业专业版 | 20,000 |
| 商业旗舰版 / 企业版 | 50,000 |
| 购买扩容包 | 单表最高 200 万（单个 Base 总行数 1,000 万） |

超限错误码 `1254103 RecordExceedLimit`。

**结论**：存在"升级飞书版本 / 买扩容包换取 6–12 个月"的低成本路径，但它只解决容量，不解决下面三个已经在产生成本的结构性问题。

### 真正的迁移动机（比容量更重要）

1. **无 JOIN、无聚合** —— `student.service.ts` 的 `matchesNonQ()`（:135-155）靠内存过滤兜底，多条件 OR 无法下推，数据量一大列表就慢。
2. **无批量写入** —— `BaseClient` 只有单条 `create`，200 条一批串行。邮件归档的性能问题根因在此。
3. **每次查询都是 HTTP 往返**，叠加 QPS 限流（`1254290 TooManyRequest`）与写冲突（`1254291`）。

## 二、现状盘点（2026-09-07 实探）

### 2.1 好消息：抽象层已经就绪

| 项 | 结论 |
|---|---|
| 唯一注入点 | `apps/api/src/base.provider.ts` 的 `BASE_CLIENT` |
| 接口规模 | `BaseClient` 共 **12 个方法** |
| 依赖范围 | 40 个文件 import `@acms/base-adapter`，36 个 service 注入 |
| 绕过情况 | **零绕过** —— 全仓无直接请求 `bitable/v1` 的 fetch |

> 这是本方案可行性的地基：只要写一个同接口的 `SqlStore` 并在 provider 里按表路由，**36 个业务 service 可以一行不改**。

`BaseClient` 方法清单：
`search` / `get` / `create` / `update` / `delete` / `listFields` / `updateField` / `createField` / `deleteField` / `addFieldOptions` / `listTables` / `createTable`

### 2.2 好消息：查询语义极简

全仓实际用到的过滤操作符只有 **3 个**：

| 操作符 | 出现次数 |
|---|---|
| `contains` | 30 |
| `is` | 2 |
| `isNot` | 1 |

再叠加默认的 `is` 与空值判断，`FilterGroup → WHERE` 的动态 SQL 生成器是**几十行代码**的量级。

代码层**不依赖**公式字段(19) / 查找引用(21) / 汇总(22) 做业务逻辑 —— 不需要在 PG 侧重算公式。

### 2.3 坏消息：字段类型比预想复杂

`docs/base-schema-snapshot.json`（2026-08-16 抓取，仅 8 张表，187 个字段）揭示的真实分布：

|---|---|---|---|---|

## 三、目标架构

```
36 个业务 service（零改动）
        ↓ @Inject(BASE_CLIENT)
   RoutingStore（按表路由）
     ↙              ↘
FeishuStore      SqlStore
（原 BaseClient）  （新增，Drizzle + PG）
     ↓                  ↓
  飞书 Base         PostgreSQL
（降级为导入源）
```

切换开关：`SQL_TABLES` 环境变量，逗号分隔表名，**逐表灰度、随时回退**。

## 四、分阶段实施计划

### 阶段 0：摸底（1–2 天，纯只读，风险为零）

- 重新抓取生产 40+ 张表的完整结构 + 行数，产出 `docs/base-schema-snapshot.<date>.json`
- 识别并单列：公式 / 查找引用 / 双向关联 / 人员 / 附件 / 自动编号 字段及其所在表
- 盘点飞书侧现存视图、仪表盘、自动化（迁移后会失效，需提前通知）
- 产出《全表字段清单 + 行数 + 类型分布 + 特殊字段清单》

> **这一步是后面所有工作的地基，必须先做。** 做完你就能看到真实风险地图，再决定是否全押。

### 阶段 1：接口化 + 骨架（3–4 天，不触碰业务）

- `BaseClient` 抽为 interface `DataStore`（12 个方法签名**完全不变**）
- 现有类改名 `FeishuStore implements DataStore`（行为零变化）
- 新增 `SqlStore implements DataStore`
- 新增 `RoutingStore`，按 `SQL_TABLES` 逐表转发
- 建 `field_meta` / `field_option` 表，模拟 `listFields()` 语义（保证 `dict.service`、`role-management.service` 不破）
- 用 1 张空表跑通全链路（此时业务 100% 仍走飞书，**线上零风险**）

### 阶段 2：Schema + 迁移脚本（4–5 天）

- 表设计：`id` (text, 原 record_id) + `data` (jsonb 全量) + `created_at` / `updated_at` + 高频字段"提列"
- 导出脚本：飞书 → JSON 落盘（可重跑、可断点续传）
- 导入脚本：JSON → PG（幂等）
- **字段级校验**：行数比对 + 抽样逐字段比对 + 特殊类型（日期/关联/附件）专项比对

### 阶段 3：双写 + 影子读（2–3 天）

- 开启双写：飞书为主，PG 为辅（PG 写失败**只告警不阻断**）
- 影子读：读飞书的同时读 PG，比对差异**只记日志不改行为**
- **差异率归零**才允许进入阶段 4
- 配套补偿任务：修复双写期间的不一致

### 阶段 4：灰度切读（3–5 天）

按表逐张切读，顺序：日志/流水表 → 高频读写表 → 主数据。

每表切换后观察 24 小时，异常立刻改回 `SQL_TABLES` 回退。

### 阶段 5：下线飞书写（2–3 天）

- 全表切读完成 → 关闭飞书写入 → 观察 48 小时 → 清理双写代码
- 飞书 Base 转为只读同步目标（若老师仍需查看）或直接冻结

**合计：约 15–20 个工作日。**

## 五、关键设计决策（待拍板）

| # | 决策点 | 推荐 | 理由 |
|---|---|---|---|
| 1 | **表结构策略** | JSONB 优先，热点字段渐进"提列" | 一次设计 40 套严格 schema 风险过高；`data jsonb` 可 100% 承接语义，再按查询热点提列加索引 |
| 2 | **主键** | 沿用 `rec_xxx` 文本主键 | 关联字段引用、前端 `id`、既有脚本全部免改；百万行级性能无感 |
| 3 | **ORM** | **Drizzle**（或 kysely），不用 Prisma | 查询是运行时动态生成的，Prisma 的静态类型优势用不上，且 JSONB 过滤要写 raw |
| 4 | **附件** | 一期继续存飞书云盘，SQL 只存 token | 改动最小；搬到 S3/本地留到二期 |
| 5 | **公式/查找引用字段** | 导出时固化为静态值，并标记 `derived: true` | 避免 SQL 侧重算；需确认这些字段是否被老师用于查看 |
| 6 | **飞书端处置** | 单向同步（PG → 飞书只读） | 保住老师查看习惯；若不需要可直接冻结 |
| 7 | **停机窗口** | 全量切换需分钟级停写 | 需确认业务可接受的窗口 |

## 六、风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 40 张表字段语义理解错 | 数据错乱 | 阶段 0 全量摸底 + 阶段 3 影子读校验 |
| 飞书侧手工建的视图/仪表盘/自动化失效 | 老师工作流中断 | 阶段 0 盘点 + 提前通知 |
| 双写期间不一致（飞书成功 PG 失败） | 数据漂移 | 写失败告警 + 补偿任务 |
| 隐式依赖飞书特有行为（如"单选值不在选项被静默丢弃"） | 切换后行为突变 | 阶段 3 影子读会暴露差异 |
| 人员字段(11) 存的是飞书 user_id | 与飞书通讯录耦合 | 存 jsonb 保留原始结构，二期决定是否解耦 |
| 学生档案表 66 字段 | 设计复杂度最高 | 单独设计，优先提列高频字段 |
