# 日常跟进 / 家校沟通 / 学生观察 / 实践活动 —— 合并设计方案

> 日期：2026-09-18 ｜ 状态：**待峰哥拍板**（确认后开工）
> 目标：把 3（或 4）个模块合并到「日常跟进」，用「记录类型」区分
> 本方案未改任何代码，全部结论来自本地代码 + 生产配置的只读核对

---

## 一、结论速览

| 模块 | 能否合并 | 理由 |
|---|---|---|
| **家校沟通** | ✅ 强烈建议合 | 与日常跟进 **18 个字段里 15 个同名同义**，只多 3 个家长字段 |
| **学生观察** | ✅ 强烈建议合 | 字段**完全照搬**日常跟进（历史就是抄的），只多 1 个「观察类型」 |
| **实践活动** | ⚠️ 不建议并表 | 字段骨架**完全不同**（活动X vs 沟通X），学生关联方式也不同 |

**一句话**：前三个本来就是「同一张表的三个视图」，合并是**回归**；实践活动是另一张表，硬并会带来远超收益的成本。

**推荐做法**：三个合一 → 一张表 + `记录类型` 字段；实践活动保持独立表，但**入口收进同一个导航分组**（视觉上仍是「学生闭环」一排），「学生全景」里保持并排展示。

## 三、合并后的设计（推荐方案）

### 3.1 表与字段

主表 = **现有「日常跟进表」**（不新建表，避免记录 id 变更 —— 见 §5 风险）。

新增/补齐 7 个字段：

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| **记录类型** | 单选 | 🆕 新增 | 日常跟进 / 家校沟通 / 学生观察（默认「日常跟进」） |
| 家长 | 依赖学生的人员字段 | 家校沟通 | 仅在「家校沟通」类型显示、必填 |
| 家长反馈态度 | 单选（字典） | 家校沟通 | 同上 |
| 家长反馈 | 多行文本 | 家校沟通 | 同上 |
| **观察类型** | 单选（字典） | 学生观察 | 仅「学生观察」类型显示、必填 |
| 关联学生编号 | 关联学生档案 | 家校沟通 | 只读，写入时自动回填 |
| 关联监护人 | 关联监护人表 | 家校沟通 | 只读，写入时自动回填 |

合计约 **25 个字段**（原 18 + 新 7）。作为对照：硬并实践活动会到 **38 个字段**，且其中 13 个字段在两套体系里互不相通。

### 3.2 交互设计

**列表页**（`/daily-followups`）

- **记录类型**作为第一列，用彩色标签区分（日常跟进 / 家校沟通 / 学生观察）
- 顶部加**类型筛选**（多选），默认「全部（按权限可见的类型）」
- 表头**跟着筛选走**：
  - 筛「日常跟进 / 家校沟通」→ 学生 · 沟通人 · 沟通方式 · 沟通主题 · 沟通时间（与现在一致）
  - 筛「学生观察」→ 学生 · 观察人 · 观察类型 · 主题 · 观察时间（与现在一致）
  - 选「全部」→ 用中性表头：学生 · 记录人 · 方式/类型 · 主题 · 时间
- 搜索、导出、批量选择、AI 面板全部沿用现有能力

**新建/编辑表单**

- 顶部「记录类型」选择器；字段组按类型**动态显隐 + 标签动态换词**：

| 记录类型 | 显示 | 隐藏 | 标签变化 |
|---|---|---|---|
| 日常跟进 | 基础字段 | 家长组、观察类型 | 沟通X |
| 家校沟通 | 基础字段 + 家长组（家长必填） | 观察类型 | 沟通X |
| 学生观察 | 基础字段 + 观察类型（必填） | 家长组、**沟通方式** | 沟通X → 观察X |

**详情页**（`/daily-followups/[id]`）

- 一个详情页按类型渲染对应字段（现状三个详情页合并成一个）
- **AI 总结按钮全类型开放**（现在只有家校沟通有 —— 这是个顺带的功能升级，三类的 ai-summarize 配置本来就齐全）
- 「关联笔记」面板沿用，`entityType` 按记录类型动态取

### 3.3 权限设计（关键：老角色配置零改动）

把「记录类型」变成**权限维度**：

| 现有菜单权限 | 合并后效果 |
|---|---|
| `dailyfollowup:read` | 只看得到「日常跟进」类型 |
| `communication:read` | 只看得到「家校沟通」类型 |
| `observation:read` | 只看得到「学生观察」类型 |
| 三个都有 | 看得到全部 + 类型筛选器可用 |

- 后端列表接口按调用者拥有的类型权限**过滤返回类型**；新建时也只能选有写权限的类型
- **现有角色配置不用动** —— 谁原来能看什么，合并后还是能看什么
- 类型筛选器的选项**只列出有权限的类型**，不会出现「点了说没权限」

> ⚠️ 这是行级过滤，要按项目既有约定走 `RecordMeta` + 类型维度（不能用物理列过滤），实现时我会按 `rowScope` 的既有模式做。

### 3.4 菜单与路由

**✅ 已定稿**：菜单**合并为一个入口**（对外名称定为「**学生记录**」），旧路由 301 重定向。

| 旧地址 | 合并后 |
|---|---|
| `/daily-followups` | 主入口（带全部类型筛选） |
| `/home-school-comms` | 301 → `/daily-followups?type=homeschool` |
| `/student-observations` | 301 → `/daily-followups?type=observation` |
| `/home-school-comms/[id]`、`/student-observations/[id]` | 301 → `/daily-followups/[id]`（**id 不变**，所以能直接跳） |

- 侧边栏「学生闭环」分组里的 3 项 → 1 项
- 外部书签、导出链接、已发出的通知都不会失效
- 旧的 `/export/dailyFollowup` 等导出别名继续保留（导出走同一份）

## 四、实践活动：为什么建议不并表

你的需求是「看一下是否能合并」。技术上能，但我不建议 —— 三个硬障碍：

1. **字段语义无法映射**：「活动名称」硬写成「沟通主题」、「活动内容」硬写成「沟通总结」只会制造混乱；而 13 个活动字段在沟通体系里没有对应物。
2. **学生关联方式不同**：实践活动走「关联学生编号」（按 ID，稳定），其余三张走「关联学生」（按姓名，**有同名风险**）。合并必须二选一，选 ID 要改三张表的学生关联逻辑（牵动行级数据范围、学生全景、报表），选姓名则把实践活动降级。
3. **状态体系不同**：沟通类有「待办事项/责任人/截止日期/闭环状态/闭环日期」一整套闭环，实践活动只有「安全确认状态」。并表后字段组会有 2 套状态机。

**三个可选做法：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 实践活动保持独立表与页面，仅**入口归到同一导航分组**，「学生全景」里并排展示 | 几乎为零 |
| B | 做**联合列表页**（前端跨表合并展示，点击分别进各自详情） | 分页/排序/导出/统计都要单独实现，且两个表的分页无法真正合并，体验会打折 |
| C | 硬并进主表（类型=实践活动 + 动态字段组） | 单表 38 字段、两套字段组、学生关联方式统一、迁移与回归测试量翻倍 |

如果你要的是「在一个列表里能看全学生的所有记录」，方案 A + **学生全景**已经满足了；如果你要的是「一个页面录入所有类型」，那需要 C —— 但我会建议先做 A，跑一段时间看真实使用再说。

## 五、数据迁移（确认后执行，带备份与回滚）

### 5.1 关键风险：记录 id 必须保留

有**两处**依赖记录 id 的关联，id 变了就断：

1. **「得到大脑」笔记绑定** —— 按 `实体类型 + 记录 id` 绑定（`entityType="家校沟通"` + `entityId`）
2. **笔记转换记录表** —— 存了「目标记录ID」回填

→ 迁移采用**保留原 id 原样搬移**，不重新生成 id。搬完后笔记关联与转换记录**无需任何改动**。

⚠️ 待确认项：三张表的记录 id 是否全局唯一（若冲突需加前缀，那两处关联就要同步改）。这个取数时一并核对。

### 5.2 迁移步骤（6 步，可回滚）

1. **备份**：主表 + 两张源表全量 dump（保留 14 天）
2. **加字段**：主表补 §3.1 的 7 个字段（`acms_fields` + 表结构）
3. **搬记录**：源表记录原 id 写入主表，`记录类型` 分别打「家校沟通」/「学生观察」
4. **抽样校验**：条数逐一相等 · 附件字段完整 · 抽样 10 条逐字段比对
5. **关联校验**：抽查笔记关联面板能否正常显示 · 学生全景条数一致 · 类型权限过滤正确
6. **源表置只读**（保留 30 天，确认无问题后归档，**不删**）

### 5.3 待补数据（确认方案后我第一时间取）

- 三张表各自记录条数（决定迁移耗时与窗口）
- 记录 id 是否有冲突
- 有多少角色/用户分别持有这三个菜单权限（决定权限回归测什么）

> 说明：本轮生产库只读查询需要人工审批、本次未获授权，所以以上三项我没取到，**没有估算数字**。取数只需一条 SQL，方案确认后立即补。

## 九、已定稿的决策（2026-09-18）

| 决策点 | 结论 |
|---|---|
| **实践活动** | ✅ **保持独立表与页面**，只把入口收进「学生闭环」同一导航分组 |
| **菜单** | ✅ **合并成一个入口**，旧三个菜单项收掉；旧地址 301 重定向 |
| **入口名称** | ✅ 对外统一叫「**学生记录**」 |

### 配套约定：对外名 vs 内部名（重要，避免改出新问题）

「学生记录」是**界面文案**，内部标识不跟着改 —— 否则要动 30+ 处接口引用与权限别名，风险远大于收益：

| 层 | 用什么名 | 理由 |
|---|---|---|
| 菜单 / 标题 / 面包屑 / 详情页 | **学生记录**（含英文 `Student Records`） | 用户可见，跟着改名走 |
| 前端路由 | 新增 `/student-records` 作主入口 | URL 用户可见，保持一致 |
| 后端接口 | **保持** `/api/v1/daily-followups` | 接口名用户不可见，改动面 30+ 处，无收益 |
| moduleKey / 权限点 | **保持** `dailyFollowups` 等 4 个 key | 角色配置里存的就是这些 key，改了等于全员权限重置 |
| 表名 / 字段名 | **保持**（数据库不动） | 迁移风险最低 |

即：**改名止于界面与 URL，不动接口、权限 key 和数据库。**

### 开工前要先补的三项数据（只读，不构成改动）

1. 三张表各自记录条数（决定迁移耗时与窗口）
2. 记录 id 是否有冲突（决定笔记关联是否需要同步改）
3. 持有这三个菜单权限的角色/用户分布（决定权限回归测什么）
